A regression net thin enough to keep, wide enough to catch.

A configuration revamp across role, user, login, five configuration screens, dashboard and company — every one of them a screen where the wrong setting becomes a wrong trade. Manual retest of all of it each release does not happen; a suite that runs in CI does.

Period

Problem

The revamp changed configuration screens that the trading platform depends on. Regression here is not cosmetic: a role that keeps a permission it should have lost, or a symbol setting that saves but does not apply, is a production incident with a UI that looks fine.

The suite had to answer one question well: when this goes red, does the reader know what broke within a minute? That constraint drove every structural choice below.

What I built

01

Locators live apart from pages

Every screen has a page object, and every selector lives in a matching locator file. A markup change touches one locator file, not twelve specs — and the diff of a locator file reads like a changelog of the UI.

02

Fixtures so a spec starts where the test starts

Auth and page objects are injected as fixtures. A spec is five lines of intent instead of twenty lines of setup, which is the difference between a suite people read and a suite people skip.

03

Test data is named, not inlined

Each module has a variables file: roles, users, symbols, trading priorities. The same data drives several tests, so "why did these four fail together" has one answer.

04

Screenshots are evidence, not decoration

Visual comparisons for the summary and symbol screens are stored per run — ten before/after pairs on the defects that were raised from this work. A bug report that carries its own proof gets fixed instead of debated.

05

One static cache for the slow part

Session and reference data are cached between specs, so the suite spends its time on the screens under test rather than logging in a hundred times.

Evidence

Result

The revamp modules have a regression net that runs on every push, and failures point at a screen instead of a stack trace. Five defects in the summary screen and five in the symbol screen were raised from this work with before/after screenshots attached.

What I would do differently

  • Shard the suite in CI. It grows linearly with the revamp; one job will not stay acceptable.
  • Seed through the API, not the UI. Login as a fixture is already cached, but creating users and roles through the interface is setup pretending to be a test.
  • A tagged smoke subset, so a release check is six minutes and not the whole suite.
