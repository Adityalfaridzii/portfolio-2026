Testing the door: SSO, social login, and the account you can now delete yourself.

Every product decision at Traveloka passed through one door: how a user signs in. In two years that door was rebuilt — login and register moved to SSO and email, social login was added for a Japan and Korea expansion, and account deletion came off the support queue and became something a user could do alone.

Role
QA Engineer, Platform
Period
Feb 2024 — May 2026
Surface
iOS · Android · mWeb · API
Status
Shipped

Problem

Identity is the one domain where "it works" is never the question. The questions are: does it work for the account that already exists, on the device that is two versions behind, with the provider that returns a different payload? A sign-in screen is a small thing with a very large matrix behind it.

What I tested

01

The Login / Register V3 move to SSO and email

A revamp that changed the primary path for every existing user. The work was less "test the new screen" and more "prove the old user still gets in" — existing accounts, fallbacks, and the phone-number path that was being de-emphasised.

02

Social login for the Japan and Korea expansion

LINE, NAVER and TikTok, each with its own consent screen and failure behaviour. Every provider got the same matrix: success, failure, cancel, and linking to an account that already exists.

03

Account deletion, from support queue to self-service

The flow moved off native screens into a Web Container that reuses the MWeb version. The test of that revamp was parity: the container had to behave exactly like the flow it replaced, on a screen where being wrong means an account that cannot be recovered.

04

The onboarding slides experiment

An experiment in User Identity that had to be measured, not just shipped. Testing an experiment means testing the instrumentation: if the event does not fire, the experiment reports a winner that does not exist.

Evidence

Business-impact figures are withheld by choice. What can be stated is what was tested and what moved:

Result

The V3 revamp and the social providers shipped, and the identity domain closed a release cycle without an authentication regression reaching production. Account deletion stopped being a support queue and became a screen a user could finish alone — which is both a QA outcome and a privacy one.

What I would do differently

  • Write the identity matrix down as a document, not a checklist. Method × platform × account state is the real test plan; a list of screens is only its shadow.
  • Test the analytics as hard as the button. An experiment with a broken event is worse than no experiment, because it produces a confident wrong answer.
  • Have the deletion parity test automated. It is a perfect fit for a visual-diff run against two implementations of the same flow.
