Index/ Work/ CF-02

Replacing a spreadsheet that calculated other people's money.

A Master Calculation workbook decided whether the trading platform's numbers agreed with expected values and with the OZ system — four trade methods, three numbers each, recalculated by hand. One stale cell and the team chases a defect that does not exist. This is the tool that took over the arithmetic, and the test map that keeps it honest.

Role
Build & test, with Dya
Period
2026 — now
Surface
Web app · local-first
Status
In use

Problem

The Master Calculation file was the source of truth for "does the platform agree with expected and with OZ". It was a spreadsheet, which means it had no types, no tests, and no memory of what changed. When a number looked wrong, the honest answer was usually "recalculate it and see".

The failure mode is specific and nasty: a spreadsheet bug and a product bug look identical from the outside. QA time goes into proving which one it is before the real investigation can start.

What I built

01

Embedded Postgres, not a database server

PGlite gives a real Postgres engine in-process. The tool runs on a QA laptop with one command — no shared staging DB to pollute, no credentials to hand around, no "works on my machine" divergence. The schemas are real; only the hosting is unusual.

02

Calculation is pure, and tested like it

The arithmetic sits in plain modules — baseline, rounding, zero-flow, formula-input conversion — each with its own test file. Numeric code earns unit tests first, because a silent rounding difference is a wrong number nobody notices.

03

Comparing three truths, not one

For each of the four trade methods the tool shows Expected, Dashboard and OZ side by side, so a mismatch points at which layer disagrees instead of just that something does.

04

Triggering trades needs friction in the right place

The trigger page sends real trades, so it gets a default-value button, an environment banner that cannot be missed, and a mascot that makes the page unmistakably not a read-only screen. The dangerous action is the one that should feel different.

05

Rejected orders get a suggested fix, not just a red row

Failed orders are detected and paired with a proposed corrective trade. The tool does not stop at "this failed" — the useful output for the person on shift is what to do next.

06

A smoke test that puts the configuration back

An automated smoke path for trade execution covers the happy flow, a rejection and a cancellation. Each scenario is set up through the configuration API and the original settings are always restored afterwards — a smoke run must never leave an environment that someone else has to debug.

Result

The Master Calculation workbook is retired for daily work. The team checks Expected, Dashboard and OZ in one screen, triggers trades with the environment visible, and gets a suggested correction when an order is rejected. The how-to documentation ships with the tool, written for the people who use it rather than for the people who built it.

What I would do differently

  • A browser-level test for the trigger flow. The logic is tested hard, but the click-to-send path deserves one end-to-end test that fails if the button ever fires against the wrong environment.
  • Run the smoke test from a CLI, not the app. It exists and restores its own configuration; a terminal one-liner would let it run in CI where a browser is inconvenient. That is the next step, not a rewrite.
  • Test names as documentation. The file names are clear; the block names inside are not always. A reader should learn the rule from the test title alone.
